## 一、流式输出（Streaming）：为什么要它，它到底是什么

### 先看一组本鱼实测的数字（同一问题、同一模型）

| 方式 | 用户看到第一个字 | 全部完成 |
| --- | --- | --- |
| 非流式 | **1.25 秒后**（一次性出现） | 1.25 秒 |
| **流式** | **0.62 秒**（之后逐字蹦） | 1.25 秒 |

**总耗时完全一样**，但**感知速度差一倍**。
用户等 0.6 秒看到字在动，和干等 1.25 秒，心理感受是天壤之别。

> ★ **记住这个指标体系**：
> - **TTFT**（Time To First Token，首字延迟）→ 直接决定"感觉快不快"
> - **TPS**（Tokens Per Second）→ 决定"读起来跟不跟得上"
> - **总耗时** → 决定"这个功能能不能用"
>
> 面试聊性能优化时，说得出这三个词的人，和别人立刻不是一个层次。

### 它到底是什么：SSE，不是 WebSocket

```
底层：HTTP + Server-Sent Events（SSE）
     服务端把一次响应切成很多小片，边生成边推
     客户端收到一串 data: {...} 事件，最后以 data: [DONE] 结束
```

**关键点**：它**不是长连接的双向通道**（那是 WebSocket），而是**一次 HTTP 请求的流式返回**。
所以：不需要额外协议、不需要握手、不需要保活逻辑 —— 但**也不能中途"发新指令"**。

### 代码上的三个坑（`stream_demo.py` 里有注释标出）

**坑 1：返回对象变了**
```python
# 非流式
resp = client.chat...create(...)      # 一个完整响应
resp.choices[0].message.content        # 直接取内容

# 流式
stream = client.chat...create(..., stream=True)
for chunk in stream:
    chunk.choices[0].delta.content     # ★ 是 delta 不是 message！
        # 而且 delta.content 可能是 None（首块/尾块没有内容）
```
→ **必须判空**，否则 `None + str` 直接崩

**坑 2：usage 只在最后一个 chunk 有 —— 而且默认还不在**
```python
stream_options={"include_usage": True}   # ★ 不加这个，chunk 里根本没 usage 字段
```
**这直接决定你还能不能算成本** —— 忘了它，你的流式程序就是个瞎子。

**坑 3：`chunk.choices` 可能是空的**
最后一小块只带 usage，`choices` 是 `[]` → 访问 `chunk.choices[0]` 会 IndexError。

### ★ 生产环境的真问题：中途断了怎么办

这是本课**最容易被忽略、面试最容易加分**的点：

> 非流式失败 → 可以静默重试，用户无感。
> **流式失败 → 用户已经看到一半内容了，你重试的话会重新生成一遍，用户看到重复。**

**三种处理策略**（各有代价，必须选一个）：

| 策略 | 做法 | 代价 |
| --- | --- | --- |
| A. 静默重试 | 清屏重来 | 用户看到内容"闪回"，体验差 |
| B. 明示重试 | 提示「连接中断，正在重试…」再重来 | 稍微啰嗦，但**诚实、可控** ← 本课采用 |
| C. 断点续传 | 把已生成内容作为前缀塞回去继续 | 成本翻倍、且模型不保证接得上 |

**本课选 B**，理由：**诚实的行为 > 聪明的技巧**。面试被问到时，说出三种策略和取舍，比只会说"我加了个 retry"强太多。

## 二、错误重试：先分类，再谈重试

### ★ 第一原则：**不是所有错误都该重试**

`retry_demo.py` 里有一张「错误分类表」，这是本课的核心：

| HTTP | 异常类 | 什么意思 | 该重试吗 | 怎么处理 |
| --- | --- | --- | --- | --- |
| **401 / 403** | `AuthenticationError` / `PermissionDeniedError` | key 错/无权限 | ❌ **绝对不重试** | **立刻报错退出**（重试一万次也没用，还白烧时间） |
| **404** | `NotFoundError` | 模型名不存在 | ❌ 不重试 | 提示检查模型名 |
| **400** | `BadRequestError` | 参数错（如 max_tokens 越界） | ❌ 不重试 | 报错，改代码 |
| **429** | `RateLimitError` | 限流/配额 | ✅ **必须重试** | **指数退避 + 随机抖动** |
| **5xx** | `InternalServerError` | 服务端故障 | ✅ 重试 | 指数退避 |
| — | `APIConnectionError` | 网络不通/断开 | ✅ 重试 | 指数退避 |
| — | `APITimeoutError` | 超时 | ✅ 重试 | 指数退避 |

**一句话**：**4xx 里只有 429 该重试，其他 4xx 重试就是浪费生命；5xx 和网络问题才该重试。**

### 指数退避 + 抖动（得会算）

```python
delay = base * (2 ** (attempt - 1))     # 1s → 2s → 4s → 8s
delay += random.uniform(0, delay * 0.5) # ★ 加抖动，防止"惊群"
delay = min(delay, max_delay)           # 封顶，别退避到天荒地老
```

**为什么要「抖动」（jitter）**：如果服务端限流了 1000 个客户端，它们都严格等 1s、2s、4s，
就会**在同一时刻同时重试**，把服务端再打垮一次（这叫 thundering herd，惊群）。
随机抖动让重试时刻错开。

> ★ 面试直接考这个：**「什么是指数退避？为什么要加 jitter？」** —— 能答出惊群的，是少数。

### ★ 一个必须知道的坑：SDK 自己已经在重试了

`openai` SDK **默认自动重试 2 次**（针对连接错误、429、5xx）。
所以你在外面又包一层重试，**实际请求次数是乘法关系**（3 × 3 = 9 次）。

**正确做法**：要么关掉 SDK 的重试自己控制，要么知道自己有几层：
```python
client = OpenAI(..., max_retries=0)   # 关掉 SDK 自动重试，自己接管
```
本课脚本**显式关掉**，让你看清每一次尝试。

## 三、成本统计：流式下怎么算

### 核心公式（写进代码注释里）

```
未命中输入：cache_miss_tokens × 输入单价
命中输入  ：cache_hit_tokens  × 缓存单价（约 1/50）
输出      ：completion_tokens × 输出单价
```

**本课脚本按「高峰价」保守估算**（宁可高估）：
- 输入未命中 ¥2 / 1M
- 输入命中 ¥0.04 / 1M
- 输出 ¥8 / 1M

> ⚠️ **价格会变**：2026-05 DeepSeek 宣布过永久降价。**代码里必须写清「价格来源 + 日期」**，
> 否则你三个月后看自己的成本表就是错的。

### 多轮对话的成本陷阱

命令行问答程序是**多轮**的 —— 而每一轮都要把**前面所有轮次**重新发一遍！

```
第 1 轮：输入 50 token
第 2 轮：输入 50 + 上一轮输出/输入 ≈ 150 token
第 3 轮：≈ 250 token
...
第 10 轮：可能已经 1500+ token
```

**输入 token 是平方级增长的** —— 这就是「多轮对话越来越贵」的原因，
也是后面 RAG/Agent 必须做**上下文管理**（摘要、截断、只保留相关历史）的原因。

> ★ 这正是**缓存命中**的用武之地：前几轮的内容是**不变的前缀**，会命中缓存。
> 本课脚本会把每次的 `cache_hit` 打出来，你跑几轮就能亲眼看到命中率上升。
