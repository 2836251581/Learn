## 一、第一遍：看清楚骨架（3 件事）

任何一次大模型调用，都只有三件事：

```
① 我是谁    → api_key + base_url（身份和门牌号）
② 我说什么  → messages（system + user）
③ 我要什么  → model + temperature + max_tokens
```

代码里对应：

```python
client = OpenAI(api_key=..., base_url=...)   # ①
resp = client.chat.completions.create(
    model=MODEL,                              # ③
    messages=messages,                        # ②
    temperature=0.7,                          # ③
    max_tokens=500,                           # ③
)
```

**记住这个骨架**。后面无论你学 RAG、Agent、还是多模态，**骨架永远不变**：
（身份 + 门牌）发起请求 →（消息列表）说清上下文 →（参数）控制输出。

## 二、第二遍：三个必须讲得出的点

### ★ 点 1：`base_url` 为什么可以随便换 —— 「接口兼容」的真实边界

```python
BASE_URL = "https://api.deepseek.com"    # 换成阿里的、硅基流动的、智谱的……
```

**一句话结论**：国内主流大模型厂商都实现了 **OpenAI 兼容协议**，所以换平台只改这一行。

**为什么这对你重要**：
- 你学的是**协议**，不是某个厂商的 SDK —— 这是可迁移能力
- 你项目里可以「一套代码多平台跑」→ 这本身就是项目亮点（成本对比、故障降级）

**★ 但边界在哪（这是加分项，一般人答不上来）**：

| 能力 | 兼容程度 |
| --- | --- |
| 普通对话 | ✅ 基本完全兼容 |
| 流式输出 | ⚠️ 大体兼容，细节（结束标志、usage 回传时机）各家有差 |
| 工具调用（function calling） | ⚠️ **分叉明显**：流式返回时 `tool_call` 的 ID 累积策略各家不同 |
| 结构化输出（JSON Schema 约束） | ❌ 支持度参差不齐，有的只支持 `json_object` |
| 多模态、缓存计费 | ❌ 完全各搞各的 |

> **面试怎么答**：「兼容协议只到简单对话层面。一涉及工具调用和结构化输出就分叉了 ——
> 我在项目里做过一层薄封装来抹平差异。」← 这么说你就比 90% 的人强。

---

### ★ 点 2：`temperature` 到底是什么旋钮

```python
temperature=0.7    # 0 = 几乎确定，1.5 = 很放飞
```

**一句话结论**：`temperature` 控制**采样时的随机性**，本质是在「按概率抽取下一个 token」时
把概率分布**变得更平（随机）或更尖（确定）**。

**必须知道的细节**（面试真题级别）：

| 说法 | 对不对 |
| --- | --- |
| `temperature=0` 时输出完全确定、每次都一样 | ❌ **错**。是「几乎确定」 |
| 为什么不是完全确定 | 因为 GPU 浮点运算顺序、批处理合并、MoE 路由等都会引入微小差异 |
| 什么时候必须用 0 | 评测、抽取结构化数据、要可复现的实验 |
| 什么时候要调高 | 头脑风暴、文案、需要多样性时 |

**★ 本鱼实测（2026-10-11，`deepseek-chat`）** —— 这个结果值得你亲眼看一次：

```
temperature = 0.0  第 1 遍 → 鲸语汐 / 蓝汐 / 鲸小灵
temperature = 0.0  第 2 遍 → 鲸语 / 汐音 / 澜心      ← 不一样！
temperature = 1.1  第 1 遍 → 鲸语灵 / 沫汐 / 蓝澜
temperature = 1.1  第 2 遍 → 鲸落 / 汐语 / 蓝溯
```

**两个结论**：
1. `temperature=0` **仍然不可复现** —— 很多人以为设 0 就能完全确定，**这是错的**
2. 由此推出的工程要求：**做评测（第 7 周）时，不能用「跑一次对比一次」的方法**。
   必须：多次运行取平均、固定随机种子（如果平台支持 `seed` 参数）、
   或者用**基于规则的指标**（命中率、召回率、是否包含标准答案）而不是肉眼看输出

> ★ **这个发现直接决定了你第 7 周评测集的设计**。记住它。

### ★ 点 3：token 和成本 —— 你项目二的灵魂

```python
cost = estimate_cost(usage.prompt_tokens, usage.completion_tokens)
```

**一句话结论**：模型按 **token** 计费，输入和输出**单价不同**（输出通常贵 3-4 倍）。

**为什么本鱼盯着这一行不放**：

方案调研里的原话：**「62% 的企业把『运营成本预测失败』列为 AI 落地最大的扩展障碍。」**

也就是说：**会算成本的人，比会调 API 的人稀缺得多。**

**你要养成的三个习惯**：

1. **每次调用都看 `usage`** —— 别当它不存在
2. **算单位成本** —— 「这个功能单次请求约 X 元，一万次约 Y 元」
3. **知道成本的杠杆在哪**：
   - 输入 token：靠**减少上下文**（RAG 的检索精度直接影响你的成本！）
   - 输出 token：靠**限制 max_tokens / 让模型说短话**
   - 缓存命中：DeepSeek 有**缓存命中折扣**（同样的前缀会便宜很多）

> ★ **这条要划重点**：RAG 系统的成本和检索质量是**直接挂钩**的 ——
> 检索回来 20 个 chunk 比 5 个 chunk 贵 4 倍，但准确率可能没提升。
> **这就是你第 6-7 周做「混合检索 + Rerank + 评测」的真正动机**，不只是为了好看。

## 三、动手实验（★这是本课的核心任务）

本鱼给你写好了一个实验脚本：`code/run_experiments.py`

**它做什么**：同一个问题，用 `temperature = 0 / 0.7 / 1.5` 各跑一次，打印输出和成本。

**你要做**：
1. 读一遍 `run_experiments.py` 的代码（很短，注意它怎么复用成本计算）
2. 跑它：`..\.venv\Scripts\python.exe run_experiments.py`
3. **观察三次输出的差异**，把结论写进你的笔记

**跑之前先猜一下**（这叫「先预测再验证」，是工程思维的核心习惯）：
- `temperature=0` 两次跑会不会完全一样？
- 1.1 的输出会不会开始乱跳？

**★ 跑完你会发现一件事：连 `temperature=0` 两遍都不一样。**
别急着说「脚本有 bug」—— 先去查「为什么 LLM 在 temperature=0 时仍不可复现」，
再回来对着你的观察写结论。**这个发现比跑通程序本身值钱。**

### 进阶挑战（选做，但强烈建议）

在 `run_once()` 里给请求加上 `seed` 参数，看能不能把 `temperature=0` 的输出固定住：

```python
resp = client.chat.completions.create(
    model=MODEL,
    messages=[...],
    temperature=temperature,
    max_tokens=300,
    seed=42,          # ★ 加上这一行，试试
)
```

**注意观察**：加了 seed 之后真的能复现吗？
（提示：不是所有平台都完整支持 `seed`，DeepSeek 的文档说法值得你去查一次 ——
**自己去官方文档找答案是这项挑战的真正目的**）
