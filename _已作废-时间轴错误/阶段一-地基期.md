# 阶段一 · 地基期（2026.10 – 2026.12，共 12 周）

> **独特目的**：从"会写 Python 的学生"变成"能独立做出一个 AI 应用的开发者"。
> 结束时你应该有一个能讲 20 分钟的项目，和一套不会拖后腿的工程基础。

---

## 这 12 周结束时，你必须能做的事

- [ ] 熟练使用 Git（commit/push/branch/看 diff），有自己的 GitHub 仓库
- [ ] 用 venv 管理环境，知道为什么不能用全局 Python
- [ ] 调用至少 2 家模型厂商的 API，理解请求/响应结构、token、计费
- [ ] 实现流式输出、错误重试、多轮对话、token 统计
- [ ] 理解 Embedding 和向量相似度，能手写语义搜索
- [ ] 会用 SQL 做多表查询和窗口函数
- [ ] 能用 FastAPI 把自己的代码变成 HTTP 服务
- [ ] 会用 Docker 把服务打包成镜像
- [ ] 完成**项目一（垂直领域 RAG）**并开源

---

## 逐周计划

### 第 1 周（10.12–10.18）｜环境与 Git

**学**
- 虚拟环境原理：为什么每个项目要独立环境
- Git 四个核心命令 + `.gitignore` 的作用

**做**
- 按 `开局配置.md` 完成 5 步开局
- 建 `ai-learning` 仓库，跑通 `hello_llm.py`，提交第一次

**验收**：GitHub 上有一个 commit，内容是能跑的 LLM 调用代码。
**踩坑预警**：Windows PowerShell 执行策略可能拦住 venv 激活，见开局配置。

---

### 第 2 周（10.19–10.25）｜Python 工程化

**学**
- 模块与包的组织方式（`__init__.py`、相对导入）
- 异常处理（`try/except/else/finally`，自定义异常）
- 类型注解（`typing`）—— 现代 Python 项目基本都要
- 日志（`logging`）而不是 `print`
- 配置文件（`.env` + `python-dotenv`）

**做**
- 写一个多文件的小工具：比如**批量文件整理器**（按扩展名/日期分类）
- 用日志记录每一步，用配置文件控制行为

**验收**：一个 3 个文件以上的项目，有日志、有异常处理、有配置。
**为什么这周重要**：后面所有项目都建立在这套规范上。跳过这周，后面代码会变成一坨。

---

### 第 3 周（10.26–11.01）｜第一次真正调用大模型

**学**
- Chat Completions API 的结构（messages / role / system prompt）
- system / user / assistant 三种角色的作用
- Prompt 的基本要素：角色设定、任务描述、输出格式约束、示例（few-shot）

**做**
- 做一个命令行问答程序，支持多轮对话（维护 messages 列表）
- 试三种不同的 system prompt，观察输出差异

**验收**：能连续对话的命令行程序，且理解了 messages 数组是怎么增长的。

---

### 第 4 周（11.02–11.08）｜API 工程细节（这周最关键）

**学**
- **流式输出**（SSE）：为什么聊天界面能一个字一个字蹦出来
- 错误处理：超时、限流（429）、服务端错误（5xx）怎么应对
- 重试策略：指数退避是什么，为什么要它
- token 计费：input/output token 分别怎么算钱

**做**
- 给上周的程序加上：流式输出 + 自动重试 + token/费用统计
- 让程序在退出时打印本次会话总花费

**验收**：程序能流式输出、能在限流时自动等待重试、能准确报出花费。
**踩坑预警**：流式响应是**逐块（chunk）到达**的，不是完整 JSON，需要拼接增量。

---

### 第 5 周（11.09–11.15）｜Embedding 与语义检索

**学**
- Embedding 是什么：把文本变成向量
- 余弦相似度：为什么它适合衡量语义相似
- 向量检索的基本流程：建库 → 查询 → 排序

**做**
- 用 Embedding API 把 100 条文本向量化
- 实现一个语义搜索：输入一句话，找出最相近的 5 条
- **对比实验**：关键词搜索 vs 语义搜索，找出语义搜索赢和输的例子

**验收**：能解释"苹果手机"和"iPhone"为什么关键词搜不到但语义能搜到。

---

### 第 6 周（11.16–11.22）｜SQL 复习强化

**学**
- JOIN 的各种类型及其语义差异
- 窗口函数（`ROW_NUMBER` / `RANK` / `LAG` / 累计和）
- 聚合与分组、`HAVING` 与 `WHERE` 的区别
- 执行顺序（FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY）

**做**
- 找一个真实数据集（Kaggle / 天池随便挑一个），写 30 条查询
- 至少 10 条要用到多表 JOIN 和窗口函数

**验收**：给你一个业务问题，你能直接写出 SQL，而不是"先取出来再用 pandas 处理"。
**为什么这周值得投入**：SQL 是数据岗和 AI 应用岗**共同要求**的技能，你的专业底子在这里能变现。

---

### 第 7 周（11.23–11.29）｜FastAPI 服务化

**学**
- FastAPI 的基本结构：路由、请求体校验（Pydantic）、依赖注入
- 自动生成的 Swagger 文档（`/docs`）
- 异步（`async/await`）在 IO 密集型场景为什么重要

**做**
- 把第 4 周的问答程序包成 HTTP 接口
- 实现 `/chat`（普通）和 `/chat/stream`（流式，用 SSE）
- 访问 `/docs` 测试接口

**验收**：能用 curl 或浏览器直接调用你的服务，并看到流式返回。

---

### 第 8 周（11.30–12.06）｜Docker 与 Linux

**学**
- 镜像 vs 容器的区别（不用背，理解就行）
- Dockerfile 基本指令：`FROM` / `WORKDIR` / `COPY` / `RUN` / `CMD`
- 端口映射、环境变量传入
- 常用 Linux 命令：`ls` / `cd` / `cat` / `grep` / `ps` / `top` / `df` / `chmod`

**做**
- 把 FastAPI 服务写成 Dockerfile 并跑起来
- 用 `docker run -e` 传入 API Key（从环境变量，不硬编码）

**验收**：`docker run` 之后服务能正常响应。
**踩坑预警**：Windows 上 Docker Desktop 需要 WSL2。装它可能耗时较久，安排在这周而不是急着用的时候。

---

### 第 9 周（12.07–12.13）｜★项目一启动：文档解析

**学**
- 为什么真实文档是"脏"的：双栏、表格、页眉页脚、扫描件
- PDF 解析的基本工具和局限（文字层 vs 图像层）

**做**
- **选定领域**（关键决策，见 `项目作品集.md`）：建议选一个专业性强、公开可得的文档集
- 下载语料，写解析脚本，把 PDF 变成结构化文本
- 特别处理：表格怎么保留结构、页眉页脚怎么去掉

**验收**：解析出的文本**没有乱码、没有重复页眉、表格信息没丢**。
**踩坑预警**：解析质量直接决定 RAG 上限。**"garbage in, garbage out"**，这周别偷懒。

---

### 第 10 周（12.14–12.20）｜★项目一：切分与向量化

**学**
- Chunking 策略：固定长度 vs 按语义/标题层级
- chunk 太大 / 太小分别有什么问题
- 元数据的重要性（来源、章节、页码）

**做**
- 实现至少 2 种切分策略，对比检索效果
- 建向量数据库（入门用 Chroma，或直接用 numpy 自己存）
- 跑通端到端：问题 → 检索 → 拼 prompt → 模型回答

**验收**：能针对文档提问并得到有依据的回答。

---

### 第 11 周（12.21–12.27）｜★项目一：混合检索与重排

**学**
- 为什么纯向量检索会漏：专有名词、编号、缩写搜不到
- BM25 的原理直觉（关键词 + 词频 + 逆文档频率）
- Rerank（重排）：先粗召回再精排的两阶段思想

**做**
- 实现 BM25 检索，与向量检索**加权融合**
- 接入一个 rerank 模型（本地 bge-reranker 或 API）
- 观察两阶段之后的检索质量变化

**验收**：能说清楚"为什么加了 BM25 和 rerank 之后效果变好"，并给出对比数据。

---

### 第 12 周（12.28–2027.01.03）｜★项目一：评测与收尾

**学**
- 检索评测指标：Recall@K、MRR、命中率
- 生成评测：忠实度（有没有编）、相关性
- LLM-as-judge 的思路（用模型给模型打分，但要知道它的局限）

**做**
- **手工标注 50–100 条评测集**（问题 / 标准答案 / 出处）★这是核心资产
- 对比至少 4 种方案，产出数据表
- 写 README：架构图 + 数据表 + 踩坑与取舍章节
- 上传 GitHub，练 3 分钟口述

**验收**：★项目一完成。你能脱稿讲 20 分钟，且每个设计决策都能解释原因。

## 阶段一的自检（2027 年 1 月初做一次）

| 检查项 | 达标标准 |
| --- | --- |
| GitHub | 有 1 个完整项目 + 若干练习代码，commit 记录自然 |
| 项目一 | 能演示、有效果数据、README 完整 |
| 工程能力 | Git / venv / FastAPI / Docker / SQL 都能用 |
| API 能力 | 流式、重试、多轮、计费统计都会 |
| 数学 | 能画出 Transformer 流程图并讲解 |

**如果这五项没达标，不要急着进阶段二**。
阶段二是"用工具"，阶段一是"会用手"——手不熟，工具再多也做不出东西。

---

## 阶段一最容易失败的地方

1. **第 1–2 周就放弃**（配置环境太麻烦）→ 用 `开局配置.md` 照抄
2. **第 3–4 周只调 API 不做工程**（流式、重试、计费跳过）→ 这几样是面试必问
3. **第 9–12 周项目做一半**（没有评测集、没有 README）→ 项目一的核心价值就在第 12 周
4. **中途被新技术吸引跑偏** → 阶段一只做计划内的事，新的留到后面
