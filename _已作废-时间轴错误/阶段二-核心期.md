## 一条铁律：先手写，再上框架

**这是本鱼要反复强调的一点。**

错误路径（90% 的人走的）：
```
第一步就 pip install langchain
→ 照着教程敲三行代码，跑通了
→ 面试官问"Agent 的循环是怎么结束的？"
→ 答："框架自动处理的"
→ 挂了
```

正确路径：
```
第一步：自己用 30 行代码写出"问模型要工具调用 → 执行工具 → 把结果喂回去 → 再问"
→ 理解了整个循环、终止条件、消息格式
第二步：再学 LangGraph，会发现"哦，它帮我管理状态机"
→ 面试时能说清框架的价值和代价
```

> **框架是为了省事，不是为了省理解。**

## 逐周计划

### 第 13 周（01.04–01.10）｜Function Calling 原理

**学**
- 什么是 Function Calling / Tool Use：**模型不执行函数，它只是返回"我想调用这个函数和参数"**
- 工具定义的 schema 格式（名称、描述、参数及其类型）
- 消息流：`user` → `assistant(tool_calls)` → `tool(结果)` → `assistant(最终回答)`

**做**
- 定义 2 个简单工具（如"查天气""算数"）
- **不用任何框架**，手写完整循环：让模型调用工具 → 你执行 → 把结果返回给模型

**验收**：能手写出完整的多轮工具调用循环，并讲清楚每一步的消息 role 是什么。
**踩坑预警**：模型返回的**参数是 JSON 字符串**，不是 Python dict，要解析；参数可能不符合你的 schema，必须校验。

---

### 第 14 周（01.11–01.17）｜手写一个完整 Agent

**学**
- ReAct 范式：思考（Thought）→ 行动（Action）→ 观察（Observation）循环
- 循环如何终止：模型说"完成"、或者达到最大步数、或者超时
- 为什么**必须有最大步数**（否则可能无限循环烧钱）

**做**
- 把上周的循环升级成 ReAct Agent：让模型显式输出思考过程
- 加入护栏：最大步数限制、单次任务成本上限、超时
- 故意制造：工具返回错误、模型参数错误、模型陷入死循环 —— 观察会发生什么

**验收**：一个能自主选择工具、能看到思考过程、且不会失控的 Agent。
**为什么故意制造错误**：这是第 15 周"失败处理"项目的素材来源，也是真实工程的日常。

---

### 第 15 周（01.18–01.24）｜编排框架（LangGraph / 同类）

**学**
- 为什么需要编排框架：状态管理、条件分支、循环、可中断/可恢复
- LangGraph 的核心概念（如果它仍是主流）：节点（Node）、边（Edge）、状态（State）
- **框架的代价**：抽象层级高、调试困难、版本变动快

**做**
- 用框架重写第 14 周的 Agent
- 对比表：手写版 vs 框架版 —— 各多少行代码、可读性、可调试性、灵活性

**验收**：能客观说出"我什么时候会用框架、什么时候不会"，**而不是只会吹框架**。
**面试加分点**：能对框架提出批评（有理有据）的人，会被认为有独立思考能力。

---

### 第 16 周（01.25–01.31）｜★项目二启动：工具集

**学**
- 工具设计的工程规范：描述怎么写、参数怎么校验、错误怎么返回
- 工具描述（description）质量对模型选择工具的影响 ★这是很多人忽略的关键点

**做**
- 确定项目二的场景（见 `项目作品集.md`，推荐"数据查询 Agent"或"求职助手"）
- 实现 **5 个以上**工具，每个包含：
  - 清晰的 description（模型靠它决定用不用）
  - 参数类型校验
  - 结构化错误返回（不是抛异常，而是返回"失败原因"让模型能自己修正）
- 给工具写单元测试

**验收**：工具的 description 能让模型在正确场景选对工具（做 20 个测试用例验证）。

---

### 第 17 周（02.01–02.07）｜★项目二：失败处理（核心亮点）

**学**
- 失败模式分类：工具报错、API 限流、超时、参数错误、模型幻觉出假工具名
- 重试机制：指数退避、最多几次、什么情况下不该重试
- 降级策略：主工具失败后用备用方案

**做**
- 故意注入故障：让工具随机抛错、让 API 返回 429
- 实现：重试 + 降级 + 错误反馈给模型让它换个策略
- **量化**：记录简单/中等/复杂任务的成功率

**验收**：★ 有一张"任务成功率"数据表，写进 README。
**为什么这是核心亮点**：绝大多数人的 Agent 项目只演示顺利路径。**能处理失败的系统才叫系统。**

---

### 第 18 周（02.08–02.14）｜项目二：上下文与成本

**学**
- 上下文窗口的成本：为什么长对话又贵又慢
- 上下文管理策略：滑动窗口、摘要压缩、重要信息提取
- token 预算控制

**做**
- 实现对话压缩：超过一定轮数后，把早期对话摘要成一段
- 加成本统计：每次调用的 token、累计花费、单任务平均成本
- 设置预算上限（超过就拒绝或降级）

**验收**：长对话 token 消耗显著下降（对比数据），且不损失关键信息。

**学**
- 可观测性：为什么要能看到 Agent 每一步在做什么（这是线上调试的唯一手段）

**做**

**验收**：★项目二完成。能演示"故障注入 → 系统自愈"的全过程。

### 第 20 周（02.22–02.28）｜本地模型部署入门

**学**
- 量化的基本概念：FP16 / INT8 / INT4 的区别和代价
- GGUF 是什么（llama.cpp 生态）、AWQ/GPTQ 是什么（vLLM 生态）
- 显存估算：参数量 × 字节数 + KV Cache

**做**
- 用 **Ollama** 或 **llama.cpp** 在本机跑起一个 7B 量化模型（推荐 Qwen 系列）
- 做同一问题在不同量化等级下的输出质量对比

**验收**：本机能跑 7B 模型对话，且能解释"INT4 为什么比 FP16 省显存、代价是什么"。
**踩坑预警**：8GB 显存跑 7B INT4 约 4–5GB，**浏览器要关掉**（Chrome 能吃掉 2GB）。

**验收**：一个能对外提供流式对话的本地推理服务。

### 第 22 周（03.08–03.14）｜★项目三：压测与性能报告

**学**
- 关键指标：QPS（每秒请求数）、TTFT（首 token 延迟）、TPOT（每 token 时间）、吞吐
- 并发数上升时延迟怎么变（为什么不是线性的）

**做**
- 写压测脚本（`asyncio` + `aiohttp` 即可，不用上重型工具）
- 测：并发 1 / 2 / 4 / 8 / 16 下的各项指标
- 对比 FP16 / INT8 / INT4 的速度与质量
- 画性能曲线图（matplotlib），写性能调优报告

**验收**：★ 有完整的性能报告，能解释"瓶颈在哪、为什么"。
**高级玩法**：算本地部署 vs 云 API 的成本盈亏平衡点（每天多少次请求以上才值得自建）。

### 第 23 周（03.15–03.21）｜★项目四：Text2SQL 基础

**学**
- Schema 注入：大宽表怎么精简后喂给模型
- SQL 生成的常见错误：幻觉字段、JOIN 错、聚合错
- 安全边界：只读连接、危险语句拦截

**做**
- 搭一个 PostgreSQL 或 SQLite，导入真实数据
- 实现：自然语言 → SQL → 执行 → 返回结果
- 加安全校验层：拒绝 `DROP/DELETE/UPDATE`，加超时和行数限制

**验收**：能用自然语言查询你的数据库，且危险 SQL 被拦住。
**这周能吃到你的专业红利**：数据仓库、SQL 优化这些知识，让你在这类项目上比纯 CS 背景的人更有话说。

### 第 24 周（03.22–03.28）｜★项目四：纠错、可视化、评测

**学**

**做**

- 自建 60 条测试集，报告准确率
- 写 README，开源

**验收**：★项目四完成。有准确率数据、有安全机制说明、有纠错效果对比。
